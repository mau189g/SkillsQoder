## 三、简介（平台 100–300 字区间）

P8 级全栈开发助手，以统一工程纪律打通从需求到上线的完整链路。内置**文档优先门禁**：新项目、新模块、新功能、架构调整在编码前，必须先交付 `01-`～`08-` 编号项目文档（需求分析→概要设计→详细设计→数据库设计→接口设计→原型→测试计划→部署运维），文档遵循章节等级规范、内容禁止模棱两可、所有图示用 mermaid 并通过 8.8.3 解析器校验后再进入编码。技术上覆盖渐进式 JavaScript 框架（Vue 3）、中后台组件库（Element Plus）、Go 语言与 Gin 框架、Java 企业级框架（Spring Boot）、Python 异步框架（FastAPI）、Node 企业级框架（NestJS）、微信小程序与跨平台框架（uni-app），并新增**智能体与工作流编排**域（需求证据表、节点与状态变量设计、模型／知识／工具职责分离、场景推演、验收五层、发布回读）。**代码必须打磨与单测**：业务逻辑强制配套单元测试，实现后须经正确性、可读性、健壮性、性能、安全五维打磨，无证据不交付。

## 四、详细描述（市场页正文）

### 4.1 解决什么问题

多数 AI 编码的失败不在"写不出来"，而在**流程缺失**：文档与代码脱节、改完不验证、测试缺位、上线无回滚。本技能把这四件事做成硬门禁，而不是建议。

### 4.2 核心技术栈（中文名 · 括号内为英文原名）

| 分类 | 技术栈 |

| **前端框架** | 渐进式 JavaScript 框架（Vue 3）、中后台组件库（Element Plus）、状态管理（Pinia）、路由（Vue Router）、服务端渲染框架（Nuxt）、构建工具（Vite）、单元测试（Vitest） |

### 4.3 核心能力

| 维度 | 能力 |
|------|------|
| 文档优先 | 8 篇编号项目文档强制前置，编号命名 + 章节等级 + 无歧义表述 |
| 图示门禁 | 全量 mermaid，语法锁定 ≤ 8.8.3，由真实解析器逐块校验 |
| 前端 | Vue 3 `<script setup>` + TS strict、Pinia、Vue Router、Nuxt、Element Plus 速查与 CRUD 生成、独特视觉设计、企业级规范 |
| 后端 | Go + Gin、Java + Spring Boot、Python + FastAPI、Node + NestJS/Express，跨栈通用分层与统一响应 |

| 架构 | 技术选型、API 契约、数据库与分片、鉴权权限、部署与渐进式发布 |

### 4.4 工作方式

七步闭环：**分析 → 方案 → 执行 → 打磨 → 验证 → 交付 → 复盘**，按任务规模裁剪为轻量/常规/复杂三档，禁跳过打磨、验证、复盘。

### 4.5 与通用编码助手的差异

- 文档不是可选项，而是编码的**前置冻结件**，需求与接口文档冻结后作为契约。
- 图示不是"看着像就行"，而是**解析器实测通过**，杜绝在新版本能渲染、目标版本报错。
- 交付不是"写完即交"，而是**证据齐备**：命令+退出码、用例通过数、真实入口验证截图或响应体。

## 五、使用提示词（市场页示例，复制即用）

### 5.1 启动新项目（触发完整文档链）

```
用 P8 全栈开发帮我启动一个「企业订单管理系统」。技术栈：Vue 3 + TypeScript + Element Plus，
后端 Spring Boot + MySQL，鉴权用 JWT。先按文档优先门禁产出 01-需求分析说明书 到
08-部署与运维手册 共 8 篇编号文档，文档内所有图用 mermaid 并通过 8.8.3 解析校验。
文档评审冻结后再进入编码，编码完成后按五维打磨并补齐单元测试。
```

### 5.2 只要文档，不要代码

```
按文档优先门禁，为「订单管理系统」补齐需求分析说明书与概要设计说明书，
文件放在 docs/ 且带 01-、02- 编号前缀，章节遵循 #→## 1.→### 1.1→#### 1.1.1，
所有决策写"选定方案 + 理由"，禁止出现"可选/建议/视情况"，图示一律 mermaid 配色。
本轮只出文档，不写业务代码。
```

### 5.3 Vue 组件开发

```
用 Vue 3 + TypeScript 写一个订单列表组件，要求：<script setup> 语法、TS strict 模式、
props 与 emits 显式类型定义、包含 loading/空/错误/成功四种状态、表格列支持自定义排序、
用 Pinia 管理列表状态。写完后跑五维打磨（正确性/可读性/健壮性/性能/安全），
并用 Vitest 为筛选与分页逻辑补单元测试。
```

### 5.4 后端接口开发（Go / Spring Boot）

```
用 Gin 实现订单模块 REST API：路由分组、统一响应结构、参数校验、错误包装、
JWT 鉴权中间件、分页查询。要求用 Go 表驱动测试覆盖成功/边界/错误三条路径，
给出 httptest 端到端用例，并说明 2 跳上游调用者是否受影响。
```

### 5.5 Bug 根因诊断

```
排查这个偶发超时的根因：服务在压测 500 QPS 时 P99 从 80ms 涨到 2.4s，
但 CPU 和内存都不到 40%。先给排查路径与取证方法，定位到根因后再改代码，
改完给出验证证据（命令+输出），不要只给猜测。
```

### 5.6 代码审查

```
审查 src/order/ 下的全部改动，按分层清单输出：致命问题必须带
文件:行号 + 为什么是问题 + 怎么改；次要问题与可选改进分开列。
不要输出泛泛的"建议优化"，每条都要能直接落地。
```

### 5.7 图示校验专项

```
校验 docs/ 下所有文档里的 mermaid 图：把文档中每个 ```mermaid 块提取出来，
用 mermaid@8.8.3 解析器逐块验证，列出 Parse error 的块号与错误原因并修复，
目标是 PARSE-ERROR 为 0。注意 gitGraph 与 erDiagram 属性块在 8.8.3 不支持。
```

### 5.8 单元测试补齐

```
为 src/utils/calculate.ts 补齐单元测试：覆盖正常值、边界值、空值、
非法输入与异常路径，用 Vitest，断言要具体到返回值而非快照，
最后给出覆盖率数字与运行输出作为证据。
```

### 5.9 Vue2 → Vue3 迁移

```
把这个 Vue 2 项目迁移到 Vue 3：选项式 API 改组合式 API，
element-ui 换 Element Plus（中后台组件库），Vuex 换 Pinia（状态管理），
列出分阶段迁移清单与每阶段的验证方式，
每阶段保证可回滚，迁移完跑一次全量测试。
```

### 5.10 技术选型决策

```
我要做一个日活 10 万的中小型 SaaS 后端，团队 5 人熟悉 Java，暂无运维专职。
给出后端技术选型结论与理由，从 Spring Boot、Go+Gin、Node+NestJS 中选定一个，
给出分层结构、数据库选型、部署拓扑与渐进式发布方案，
要求每条决策写明选定理由与放弃其他方案的原因，不要给多个选项让我自己选。
```

### 5.11 设计一个 Agent 工作流

```
设计一个「客户跟进智能体」工作流。先还原业务七问（对象与触发、目标与结果、现状障碍、约束、依赖、范围、成功标准），
再出需求证据表（要求/来源/状态/影响模块/验收方式），然后比较架构路线并给出推荐方案与切换条件，
最后输出节点表（阶段｜动作、输入、条件职责、输出、失败路径）和状态变量表。
要求事实、流程进度、执行结果三类状态分离，明确哪些判断用规则、哪些交给模型、哪些转人工。
```

### 5.12 排查工作流"重复询问"问题

```
工作流里客户已经给过信息，智能体还在重复问同一个问题。
按"事实提取 / 状态更新 / 路由 / 回复 / 序列化"五个环节定位根因，修正对应环节的职责或公共规则，
禁止为某个客户名或某句措辞加专用判断。
修完给出场景推演记录，并明确哪些是推演结论、哪些有真实运行证据。
```

### 5.13 工作流发布与回读核对

```
接手这个工作流应用，先核实草稿版本、已发布版本与平台能力是否一致。
修改前分别备份草稿与已发布版，改完保存回读、按验收五层（结构/运行/业务/发布/展示）逐层验证，
本次只保存不发布。若保存成功但回读不一致，立即停止并说明差异，不要自动补默认值或删除节点。
```
